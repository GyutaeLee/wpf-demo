# 대여·반납 시나리오

여기 적은 상황은 구현과 테스트를 위해 가정했습니다. 실제 장애나 사용자 사례를 기록한 문서는 아닙니다. 데이터는 모두 가상입니다.

## 데이터와 요청 흐름

처음 만든 SQLite 데이터베이스에는 가상 장비 5개와 대여자 2명이 들어갑니다. 장비 상태, 대여 기록, 대여·반납 이력과 요청 결과를 저장합니다. 데이터베이스는 사용자별 로컬 앱 데이터 폴더에 생기며, 서버를 재시작해도 내용은 유지됩니다. 이미 데이터베이스가 있으면 예시 데이터를 다시 넣지 않습니다.

WPF 화면은 `ILendingApi`를 통해 로컬 API를 호출합니다. 목록·선택·입력·요청 상태는 ViewModel에서 관리합니다. 한 클라이언트 폴더에는 미확정 요청 하나를 보관합니다. 작업 키와 JSON 본문을 전송 전에 임시 파일에 기록하고 디스크에 반영한 뒤 파일 이름을 바꿉니다.

```text
입력 검증 → 요청 보관 → API 전송
                         ├─ 확정 결과 → 요청 정리 → 최신 목록·이력 조회
                         └─ 결과 미확인 → 같은 키·본문 보관 → 재시도 또는 앱 재시작 후 복구
```

대여·반납 처리는 SQLite 트랜잭션 하나에서 장비 상태, 대여 기록, 이력, 요청 결과를 함께 저장합니다. 장비 하나에는 활성 대여가 하나만 생기도록 데이터베이스 인덱스도 두었습니다.

## 가정한 상황과 확인 방법

| 상황 | 처리 | 확인 방법 |
| --- | --- | --- |
| 정상 대여와 반납 | 장비 상태와 대여 이력을 함께 갱신합니다. | API 통합 테스트와 `Basic` Windows 시연 |
| 두 클라이언트가 같은 장비를 대여 | 조회한 버전이 오래된 요청은 충돌로 돌려보냅니다. 활성 대여는 하나만 남습니다. | 동시 HTTP 요청 테스트와 `ConcurrentLoan` 시연 |
| 저장은 됐지만 응답을 받지 못함 | 저장된 요청 키와 내용으로 다시 보내고 서버의 응답 기록을 돌려받습니다. 이후 현재 장비 상태를 다시 조회합니다. | `LostResponse` 시연. 시연 설정에서 첫 대여 응답을 한 번 끊습니다. |
| API에 연결할 수 없음 | 미확정 요청과 입력을 보관합니다. 결과를 모르는 동안 새 변경은 막고 재시도를 제공합니다. | `ApiDown` 시연 |
| 앱을 종료했다 다시 실행함 | 저장된 미확정 요청을 같은 키와 본문으로 한 번 다시 보냅니다. | `RestartRecovery` 시연 |
| 목록과 이력이 커져도 화면에 한 번에 모두 가져오지 않음 | 서버에서 50개 단위로 읽고 페이지 상태를 표시합니다. | 10,000개 장비·20,000개 이력의 API 테스트와 `LargeList` Windows 화면 확인 |

요청 키가 같아도 내용이 다르면 서버는 재사용을 거부합니다. 다른 클라이언트가 먼저 상태를 바꿨다면 오래된 버전은 충돌 응답을 받습니다. 이 두 경우를 포함해 중복 요청, 저장 롤백, 서버 재시작, 잘못된 입력을 API 테스트에서 확인합니다.

## 화면 구성

[WinUI Gallery](https://github.com/microsoft/WinUI-Gallery)와 [WPF UI](https://github.com/lepoco/wpfui)의 입력 컨트롤과 화면 구성을 참고했습니다. 글자 크기와 간격, 선택·포커스 표시를 조정하고 대여자와 메모를 나란히 배치해 이력이 보이는 공간을 늘렸습니다. 이력의 대여·반납 구분과 UTC 시각도 읽기 쉽게 표시했습니다.

외부 UI 라이브러리를 추가하거나 코드를 복사하지 않고 XAML 스타일과 ControlTemplate을 직접 작성했습니다. 색상은 WPF 시스템 색상을 사용합니다. Windows 자동 시연에서 기본 화면·작은 창·최대화를 캡처했으며, 배율과 고대비 화면은 아직 직접 확인하지 않았습니다.

## 범위

API는 같은 컴퓨터의 `127.0.0.1:5187`에서 실행합니다. 장비와 대여자는 예시 데이터이며, 인증·예약·여러 서버 간 동기화는 구현하지 않았습니다. 실제 장비 관리에 사용하는 앱은 아닙니다.

## 목록이 커졌을 때

기본 데이터베이스는 장비 5개를 사용합니다. `WPFDEMO_DATASET_PROFILE=Large`를 지정해 새 데이터베이스를 만들면 장비 10,000개와 장비 하나의 대여 이력 20,000개를 준비합니다. 장비 ID와 고정된 시각 규칙으로 만드는 데이터라 실행할 때마다 무작위로 바뀌지 않습니다. 새 데이터베이스마다 데이터셋 ID는 달라지고, 기본 데이터의 대여 시각은 생성 시각을 기준으로 정합니다. 이미 있는 데이터베이스에는 `Large` 설정을 켜도 데이터를 다시 넣지 않습니다.

목록과 이력 조회는 서버에서 페이지 단위로 읽습니다. 목록은 ID 오름차순, 이력은 발생 시각과 ID 내림차순으로 정렬하며 페이지 크기는 기본 50개, 최대 100개입니다. 검색 입력은 250ms 동안 멈춘 뒤 조회하고, 앞선 요청을 취소합니다. 취소 전에 응답한 요청이 늦게 도착해도 새 검색 결과를 덮지 않도록 요청 번호도 확인합니다. WPF 목록에는 행 가상화를 켰습니다.

`scripts/Measure-Api.ps1`은 대규모 테스트 DB에서 목록·이력 응답 크기와 요청 시간을 기록합니다. Windows Actions는 준비 요청 2회 뒤 각 조회를 7회 측정해 `artifacts/performance/large-profile.json`에 저장합니다. 한 러너의 결과만으로 이전 구현보다 빨라졌다고 보거나 실제 화면 응답 시간을 추정하지 않습니다. 절대 시간 합격선도 두지 않았습니다.

## 연결이 끊긴 동안의 조회

클라이언트는 성공적으로 조회한 장비 페이지와 이력만 별도 SQLite 파일에 저장합니다. 장비 캐시는 최대 1,000개, 장비별 이력은 최대 100개입니다. 서버 연결이 끊기면 캐시된 범위 안에서 검색·필터·페이지를 계산하고 마지막 갱신 시각과 저장된 데이터 범위를 표시합니다. 전체 서버 목록을 조회한 것처럼 설명하지 않습니다. 오프라인 상태에서는 새 대여·반납 요청을 시작하지 않습니다.

API 주소와 데이터셋 ID가 바뀌면 이전 데이터셋의 캐시는 지웁니다. 캐시 DB가 손상된 경우 손상 파일을 별도 이름으로 보관하고 새 캐시를 만듭니다. 미확정 대여·반납 요청 파일은 이 처리와 분리되어 있습니다. 캐시는 조회 편의를 위한 복사본이며 서버 상태를 갱신하지 않습니다.

## 진단 파일

화면의 `진단 내보내기`는 문서 폴더에 ZIP을 만듭니다. 앱 버전, 운영체제와 런타임 버전, 프로세스 비트수, DPI, 현재 미확정 요청의 작업 ID·종류, 최근 클라이언트 요청 기록과 서버의 최근 요청 메타데이터를 담습니다. 서버 연결이 끊겨 있으면 로컬 기록만 저장하고 서버 기록이 빠졌다는 상태를 표시합니다.

클라이언트 기록은 1MB 파일 두 개로 순환합니다. ZIP에는 요청 ID, 작업 ID, 허용된 API 동작명, HTTP 상태, 소요 시간, 결과 구분만 내보냅니다. 요청 본문, 메모, 검색어, 응답 내용, 로컬 파일 경로는 내보내지 않습니다. 서버 기록은 메모리에 있는 최근 100건이며 서버 재시작 뒤에도 보존되지는 않습니다. Actions의 `Basic` 시나리오는 ZIP 항목과 메모·경로 제외 여부를 확인합니다.

## 요청 처리 책임과 상태

`PendingOperationWorkflow`는 요청 파일의 복구·보관, HTTP 전송, 응답 확인과 파일 정리를 맡습니다. `LendingViewModel`은 입력과 선택, 안내 문구, 명령 활성화와 최신 화면 조회를 맡습니다. 조회 캐시와 진단 파일의 저장은 기존 저장 클래스에서 처리합니다.

| 상황 | 요청 상태 | 보관 요청 |
| --- | --- | --- |
| 보관 요청 없음 | `Ready` | 없음 |
| 전송 전 파일 저장 | `Saving` | 저장을 마친 뒤에만 전송 가능 |
| 전송 중 | `Sending` | 유지, 중복 전송 차단 |
| 연결 단절·해석할 수 없는 응답 | `Unconfirmed` | 같은 키·본문으로 재시도 |
| 확정 응답을 받았지만 파일 삭제 실패 | `CleanupRequired` | 유지, 같은 요청으로 결과 확인과 정리를 다시 시도 |
| 확정 성공·거부와 파일 정리 완료 | `ConfirmedSuccess` / `ConfirmedRejection` | 없음, 최신 정보 조회 |
| 복구 파일을 읽을 수 없음 | `RecoveryError` | 파일 보존, 새 변경 명령 차단 |

파일 정리에 실패했다면 서버 결과를 받았다는 사실과 로컬 요청이 남았다는 사실을 구분해 안내합니다. 앱을 다시 시작하면 저장된 요청으로 결과를 다시 확인합니다. API 응답을 그대로 최신 장비 상태로 쓰지 않고 목록과 이력을 재조회하는 동작은 유지합니다.

이번 변경은 macOS의 .NET 10 테스트로 확인하며, Windows WPF 빌드·UI 시연은 변경 코드를 대상으로 별도 확인해야 합니다. 배율·Narrator·고대비의 실제 확인 결과는 [수동 확인 절차](manual-windows-check.md)에 따라 기록합니다.
